### T57 · 上下文 1.0

现成材料：`extractHeadings` 已经能从 Markdown 抽出标题、层级和行号，今天只喂预览大纲。选区上限 12000 字已经存在，超了就拒绝，不截断。文件名在标签上，语言用扩展名表示。

一次改写按这个顺序组装，低优先级先被丢掉：

1. **选区**。必须有。超过 12000 字仍直接拒绝。
2. **所在位置**。Markdown 从选区起点向上找到最近的 ATX 标题，带到下一个同级或更高级标题之前。没有标题，或不是 Markdown，就带选区前后各 40 行。
3. **文件名和扩展名**。
4. **大纲**。只发标题层级和文字，不发各节正文。

字符预算从第 4 项往第 2 项砍。选区不参与砍。

发送前的面板列出本次条目：选区、章节或邻行、文件名、大纲。用户可以去掉某一项再发。现在已有的「字符数 + 主机名」留着，清单加在它旁边。

验收：对一篇有标题的 Markdown 做改写，输出能沿用这一节里的术语和标题层级。面板看得到发了哪几段；去掉大纲后再发，请求里不再有标题列表。

T57 不做：把全文塞进 prompt、记住上一轮对话、引用别的文件、给大纲做向量索引。

工作树已按这一节落地。附加上下文的字符预算是 8000，装不下时先去掉大纲，再去掉文件名，最后去掉章节或邻行。

## 0. 一句话结论

**6byte 的文本内核成熟度明显高于它的 AI 层。** 编码无损回写、100 MB memmap 只读、grep 64.5 ms、94 ms 冷启动、147 前端 + 75 Rust 测试、三平台 CI——这些都远高于同类 v0.1 项目。而 AI 层是一条**工程质量不错的一次性管道**，还不是一个**产品**。

判据只需要一句：**把全部 AI 代码删掉，6byte 依然是一个完整、且更好的编辑器；Cursor / Zed 删掉 AI 会退化成普通编辑器。**

所以「AI native」这一格现在不是缺功能，而是缺三者：**上下文（AI 知不知道自己在改什么）、可审阅的产物（改动是不是一个可接受/拒绝的单元）、状态（能不能连续工作、花了多少）**。

## 3. 三个技术分水岭：为什么它还不 AI-native

**① 上下文：模型不知道自己在改什么。**
它拿到的是「一段字 + 一句要求」，没有文件名、没有语言、没有所在章节、没有相邻段、没有工作区。所以它只能做**文本变换**，不可能做**文档工作**——不会知道这段是 README 的安装章节、不会知道术语要与上文一致、不会知道这是一份日志所以该按日志分析。

**② 产物：没有 diff，接受是一次整段替换的赌博。**
现在的交互是：流式文字直接打进正文 → 高亮 → Tab 接受时把原文换成新文。用户看到的是「原文 + 新文并排」，不是「哪几个词被改了」。这让审核成本高到大多数人只会直接 Tab。真正的 diff 装饰器已经写好了，只是没接线。

**③ 状态：AI 是一次性动作。**
没有会话、没有历史、没有用量、没有「刚才那次为什么这么改」。补全与改写是两条互不相干的实现，面板关掉就什么都不剩。

## 4. 我理解的「AI native 编辑器」

### 4.1 定义：三个翻转

AI native 不是「AI 功能多」，而是三处结构性翻转：

1. **上下文反转**：从「人把上下文喂给 AI」变成「系统自己知道上下文」——光标位置即意图，文档结构、工作区、编辑历史都是默认可寻址的。
2. **产物反转**：AI 输出的不是「文本」，而是「**可审阅的变更单元**」——一段 diff、一个 hunk、一次可撤销的事务。文本是结果，diff 才是交付物。
3. **控制反转**：AI 能碰什么、动了什么、花了多少、发了什么出去，**默认可见**；能力边界与数据边界都是产品的一部分，而不是设置里的开关。

一句话：**AI native 编辑器 = 编辑器状态本身成为模型的一等上下文，模型的输出成为编辑器的一等事务。**

### 4.2 五层功能清单（含 6byte 现状）

| 层 | 功能 | 为什么是这一层 | 6byte 现状 |
|---|---|---|---|
| **L0 信任原语**（地基，先有才谈其他） | 一次撤销 / diff 审阅 / 发送前可见 / 成本可见 / 失败不变更 / 审计日志 | 没有这些，能力越强越危险 | 撤销 ✅、发送前可见 ✅、取消断连 ✅、成本可见 🟡（usage 丢弃）、失败不变更 🟡（见 2.2）、审计 ❌ |
| **L1 交互原语** | 光标即上下文、选区浮层、ghost text（多行）、inline diff + **逐块接受**、命令面板、`@` 引用、多轮会话可回滚 | 这是「用起来像 AI」的最小感知集合 | ghost text ✅（单行、默认关）、diff 🟡（代码在仓库未接线）、逐块 ❌、`@` ❌、命令面板 ❌、多轮 ❌ |
| **L2 上下文与索引** | 文档结构（大纲/代码块/frontmatter）、工作区根与文件树、轻量检索、编辑历史、上下文预算与可见清单 | 决定 AI 的上限；也是成本的唯一闸门 | 大纲 🟡（只给预览不喂模型）、grep ✅（未接 AI）、工作区 ❌、预算 ❌、历史 ❌ |
| **L3 Agent 能力** | tool calling（读/列/搜/写）、单文件 patch 提议、多步循环、后台任务、权限审批、checkpoint 回滚 | 把「改写」升级为「办事」；必须配 L0 才敢开 | 全 ❌（`validate_request` 直接拒绝 `tool` 角色） |
| **L4 品类分化** | 本地模型一等公民、离线可用、日志/大文件分析、文档级一致性、批量整理 | 决定「为什么是它而不是别人」 | 本地模型 🟡（Ollama 仅 mock 验证）、L2 大文件禁 AI ❌ |

### 4.3 五个常见误区

- **加个聊天侧栏 ≠ AI native**：侧栏是另一个应用，和文档没有共享状态。
- **自动补全 ≠ AI native**：补全只是「更聪明的输入法」，不改变文档工作的方式。
- **把全文塞进 prompt ≠ 上下文工程**：成本、隐私、注意力三重输；上下文工程是**选择**与**可见**。
- **能改多个文件 = agent**：没有 checkpoint 与审批的多文件编辑，是一次不可逆的批量事故。
- **模型更强 = 体验更好**：AI native 的第一体验指标是**延迟**（首 token 与接受成本）和**可审阅性**，不是模型分数。

## 5. 演进路线（按投入产出排序）

> 原则：先把「现有 AI 变可信」，再把「上下文做大」，最后才让「AI 动手」。

### Step 0 · 门禁（先做，不计入主线）
真实 Ollama 点验 + AI 首 token 延迟实测。定位里最硬的承诺（本地模型）目前只有 mock 证据。

### Step 1 · 信任闭环（1–2 天，ROI 最高）
1. **接线 `rewritePreview.ts`**：流式期间文档不动，候选渲染为旁置 diff；接受时一次 `replace`（已有 `commitRewrite` 单事务），拒绝/取消零副作用。
2. **保存闸门**：有进行中的 AI 预览时，`Ctrl+S` 先取消或拒绝，绝不让半截候选落盘。
3. **成本可见**：接已下发的 `usage`，状态栏显示本次 token 与估算费用；请求传 `max_tokens`。
4. 顺手修 2.3 的四个小 bug + 安全三件套（host 确认 / 只许 https / CSP）。

**验收**：断网、取消、超时、流式中保存、双击 Esc——文档与磁盘都保持原样；一次撤销回到改写前。

### Step 2 · 上下文工程 1.0（2–3 天）
按路线图 §7.3 实现一个**显式的 context assembler**：选区（优先）→ 前后各 40 行 / 光标所在章节 → 文件名 + 语言 + 大纲 → 附加指令；超预算从低优先级截断，并在 UI 显示「本次将发送」清单（可删可加）。

**验收**：同样是改写，模型能在输出里正确沿用文档术语与标题层级；用户能一眼看到发了什么、多少字符、去哪。

### Step 3 · 工作区一层（1–2 周）
T54 文件树 + `Ctrl+P` 命令面板 + grep 默认根切到工作区 + `@` 引用（文件 / 大纲 / 最近编辑）。

这是**所有后续能力唯一的挂载点**：没有「当前工作区」，`@` 引用、跨文件上下文、检索注入都无处安放。当前的依赖顺序是倒的——PRD 把文件树排在 M4 分发之后，而分发是放大器：在上下文层没建好之前分发，等于先把「单文件编辑器」的心智发出去，之后很难重发。

### Step 4 · 窄 Agent（探索，最后）
**只读** tool calling 起步（`list_dir` / `grep` / `read_range` / `outline`），让 AI 自己找资料回答——先不给写权限。之后才是「单文件 patch 提议 + 明确确认 + checkpoint」。**跨文件自治不建议做**：与「轻量 / 默认不上传 / 数据本机」的定位冲突，且风险收益比最差。

### 结构性配套（与上面穿插）
抽出 DocumentModel / 文档服务层（applyEdits、保存基线、按内容判 dirty）→ 拆 `App.tsx` 为 hooks（session / fileOps / shortcuts / watch / ai）→ 统一命令层与 modal 栈 → 引入 RTL 并修正 vitest include，先给保存 / 冲突 / 关窗补组件测试 → 统一 AI 传输（streamId 注册表 + 错误码）。

## 6. 与现有路线图的四处冲突

1. **反定位把自己品类里最核心的格子划掉了。** §1.4 不做笔记库（=上下文库）、不做 IDE（=执行环境）、v1 不做插件（=可扩展工具），§5.5 又把「agent 多文件操作」写进「不做」。AI native 需要的三样，几乎全在反定位清单里。
2. **依赖倒置**：文件树被当 P2 UI 功能，实际是所有上下文的**前置**。
3. **「极轻」与「AI 需要索引/历史/会话」直接冲突**：需要澄清「轻」指内核（包体、冷启动、内存），不指能力。
4. **「默认不上传全文」被实现成「只发选区」**：靠砍上下文换隐私。正解是「本地索引 + 本地模型默认 + 云端只发最小必要 + 可见的上下文清单」。

---

## 7. 结论

6byte 不需要更多 AI 功能，需要**一次结构性的收口**：

- 把 AI 从「往正文里打字」改成「产出可审阅的变更」——**代码已经躺在仓库里**（`rewritePreview.ts`），只是没接线；
- 把上下文从「一段字」扩到「一份文档、一个工作区」——路线图已写好预算，只是没实现；
- 把「AI native」从 README 的形容词，变成数据模型、交互原语和信任机制里的名词。

做到前两条，产品气质会变；第三条做完，才有资格谈「native」。

对外定位建议同步收敛为：**local-first 的纯文本 AI 工作台——AI 是右手，文本内核是本体。** 这个位置（编码无损 / 巨型日志 / 中文与内网 / 无 vault 无数据库 / 本地模型）大厂不会来，但同类开源项目（如 Tauri + 本地 AI + MCP 的 [Moraya](https://github.com/zouwei/moraya)）已经在靠近，窗口不会一直开着。
