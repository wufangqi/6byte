## 1. 定位（来自路线图，与代码一致）

- 目标用户：写文档的开发者 / 技术写作者、运营产品学生、内网与涉密环境用户。
- 反定位：不做 IDE、不做笔记库、v1 不做插件/同步/协作、不做 WYSIWYG。
- 三条红线：① AI 整段修改一次 `Ctrl+Z` 可撤销；② 保存必须保持原编码；③ 默认不上传全文。
- 性能预算：冷启动 ≤1.5 s、打开 10 MB ≤500 ms、输入 P95 ≤16 ms、3 文件常驻 ≤200 MB、包体 ≤20 MB。

> 注：红线 ①③ 对应的 AI 层尚未开始，暂无从验证；红线 ② 已有实现骨架，但存在 §7 的 P0 缺口。

## 4. 关键数据流

**打开**
`对话框/拖拽/会话恢复 → ipc.readFile → Rust fs::read 全量读入 → codec::decode（BOM → 严格 UTF-8 → chardetng）→ 返回 {content, meta, size, mtimeMs} → store.addTab（按 path 去重）→ CM6 挂载`

**保存**
`Ctrl+S / Ctrl+Shift+S → 无 path 时弹保存框 → ipc.writeFile(path, content, meta) → codec::encode（按原 charset/原 BOM 编码 + 统一为原 EOL）→ 同目录临时文件 → write_all → sync_all → rename → 成功则回填 size/mtime/清脏`

**会话**
- `ainative.session`：当前打开文件的 path 列表，`tabs` 变化即写入（含每次按键）。
- `ainative.recent`：最近 12 个文件，zustand `subscribe` 全量状态变化即写入（含每次按键）。
- 启动时先恢复 recent，再在 Tauri 环境下恢复 session（逐文件重新读取）。

**拖拽/快捷键**
- 拖拽：`getCurrentWebview().onDragDropEvent`（`over`/`drop`/`leave`）。
- 快捷键：`window` 级 keydown —— Ctrl+S 保存、Ctrl+Shift+S 另存、Ctrl+O 打开、Ctrl+N 新建、Ctrl+W 关闭。
- 编辑区内建：CM6 `searchKeymap` 已带来 Ctrl+F 搜索面板（含替换输入框与正则开关）、`historyKeymap` 撤销重做、`indentWithTab`。

## 6. 本次实测

环境：Windows + DSH 沙箱（workspace-write），项目根 `D:\Documents\ai-native-editor`。

| 检查 | 命令 | 结果 |
|---|---|---|
| 前端类型检查 | `pnpm exec tsc --noEmit` | ✅ 0 error |
| Rust 单元测试 | `cargo test --manifest-path src-tauri/Cargo.toml --lib`（target 放在仓库根） | ✅ 8 passed / 0 failed，首次编译 2m16s |
| 前端打包 | `pnpm build` | ⚠️ 未能验证：`tsc` 通过后 vite 调 esbuild 子进程被沙箱拒绝（`spawn EPERM`，管道 stdio 限制） |
| 桌面端启动 | `pnpm tauri dev` | ⚠️ 未验证（需 GUI，且沙箱下同样受限） |

**环境限制（与项目缺陷无关，但会影响后续工作）**

1. 本会话沙箱的写权限 ACE 只落在工作区根目录，未继承到 `src/`、`src-tauri/` 等既有子目录，因此**shell 命令无法在这些子目录里写文件**；文件读写工具不受影响。
2. 因此 `cargo` 默认在 `src-tauri/target` 建目录会失败，需临时把 `CARGO_TARGET_DIR` 指到仓库根（本次验证用的 `.cargo-target` 已清理）。
3. 需要跑 `pnpm build`、`cargo clippy/fmt`、脚本类验证时，建议把本会话切到「完全权限（full access）」。

## 7. 问题与风险清单

### P0 — 会造成数据丢失，必须先处理

**P0-1 有损解码的文件保存时没有二次确认（踩 ADR-012 红线）**
- 路径：`codec.rs:63-72` 严格 UTF-8 失败后用 chardetng 猜测；`guess(None, true)` 允许猜成 UTF-8，非法字节被替换为 `U+FFFD` 且 `meta.lossy = true`。
- `commands.rs:61-77` 的 `write_file` **完全不看 `meta.lossy`**，直接把带 `U+FFFD` 的字符串按原编码写回 → 原来的非法字节被永久固化为替代字符，文件不可逆损坏。
- 前端只有 `StatusBar.tsx:40-44` 一个「编码有损」小标签，保存流程 `App.tsx:57-85` 无任何拦截。
- 路线图 ADR-012 要求「用户若编辑后保存，必须二次确认」，当前未实现。
- 建议：`write_file` 收到 `meta.lossy` 时拒绝或要求显式 `allowLossy: true`；前端保存前弹确认，并提供「另存为 UTF-8 / 取消」；同时考虑 chardetng 用 `allow_utf8=false` 避免「猜成 UTF-8 但解码失败」。

**P0-2 关闭脏标签、关闭窗口均无确认**
- `TabBar.tsx:36-45` 关闭按钮与 `workspace.ts:91-102` 的 `closeTab` 直接丢弃内容；`App.tsx:171-175` 的 Ctrl+W 同理。
- 没有任何 `onCloseRequested` / `beforeunload` 拦截窗口关闭。
- 建议：脏标签关闭弹「保存 / 不保存 / 取消」；窗口关闭用 Tauri `onCloseRequested` 统一拦截。

### P1 — 正确性与关键路径性能

**P1-1 每次按键都做整篇文档级工作**
- `workspace.ts:104-107`：把整个 `content` 复制进 store（大文件 = O(n) 字符串复制 + GC 压力）。
- `extensions.ts:104-106`：每次变更 `doc.toString()` 全量生成。
- `StatusBar.tsx:19-24`：每次按键 `split("\n")` 全量统计行数/字符数。
- `App.tsx:109-112` 与 `115-121`：每次按键写两次 localStorage（session + recent）。
- 结果：文档越大，输入越卡；这正是 M1「大文件」目标的直接障碍（性能预算 P95 ≤16 ms）。
- 建议：行数/字符数用 CM6 `state.doc.lines` / `doc.length`；持久化加 500 ms 防抖；store 里只存「版本号 + 增量」或让 CM6 成为唯一真源。

**P1-2 大文件 / 二进制无任何防护**
- `commands.rs:41` 全量 `fs::read`；无大小上限、无二进制探测。误开 2 GB 二进制或日志会直接吃满内存并卡死 WebView。
- 建议：M1 前至少加阈值（如 >50 MB 提示/只读）与魔数探测。

**P1-3 外部修改无感知，保存直接覆盖**
- `mtimeMs` 在 `commands.rs:29-36` 记录、在 `App.tsx:75-81` 从不比较。
- 编辑器外部改过文件后，用户在应用里保存会静默覆盖别人的修改；也无「外部已变更，是否重载」提示。
- 建议：保存前比对 mtime/size，冲突时给「保留我的 / 加载磁盘版本 / 另存为副本」三选一（路线图 §8.1 已设计）。

**P1-4 混合换行文件会被静默统一**
- `codec.rs:162-174` 的 `normalize_eol` 把全文统一成「主导换行符」。单换行文件无损，但混合 EOL（如 CRLF + LF）文件保存后行尾被改写。属于可接受取舍，但应在 README 已知限制里写明，并在状态栏区分「混合」。

## 9. 建议的下一步（按优先级）

1. **堵住两处数据丢失（1–2 天）**：lossy 保存二次确认 + 脏标签/关窗拦截。这是路线图红线 ② 的最低要求。
2. **保存冲突检测（1 天）**：mtime/size 比对 + 三选一对话框，顺带把 `file_externally_changed` 事件通道留好。
3. **按 CM6 真源重构编辑热路径（1–2 天）**：状态栏改用 `doc.lines/doc.length`、持久化防抖、store 不再每键持有全文副本。完成后用 10 MB 文件实测「打开 ≤500 ms / 输入 P95 ≤16 ms」，把 M0 未验证的两项验收补上。
4. **修架构约束与死代码（半天）**：把拖拽封装成 `ipc/api.ts` 的 `onFileDrop`；删 `addRecent`/`getActiveTab`/`baseName`。
5. **建 CI（1 天）**：三平台矩阵跑 `cargo fmt --check`、`clippy -D warnings`、`cargo test`、`tsc --noEmit`、`vite build`；先不加 E2E，等 M1 大文件稳定后再上 Playwright。
6. **再回 M1 主线**：大文件分级（阈值 + 只读视图）→ 文件监听/冲突 → 跨文件 grep；同步补 GB18030 与混合换行的编码语料测试。
7. **文档对齐**：更新 README 的「已验证/已实现/已知限制」，把 CM6 自带的查找替换写进功能列表，修正上表 §8 的漂移项。

## 10. 附：一句话总结

一个骨架干净、选型克制、编码内核已经领先于同阶段同类项目的 M0 仓库；真正的短板不在「加功能」，而在**数据安全兜底（lossy/冲突/关窗）**与**编辑热路径的 O(n) 设计**——这两件事不先解决，M1 的大文件与 M3 的 AI 都会在同一个瓶颈上撞墙。
